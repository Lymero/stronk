After M3, before M4

Stronk architecture, now and where it's heading

Two systems share one signed data contract. The pipeline turns Riot matches into per-champion build statistics; the desktop app reads them and writes runes, items and spells into the League client. No live backend: only static signed files. Section 1 covers the whole system from today to the end of M4; sections 2 to 5 go one level down.

Source: main at 02672bd (2026-10-20): code, docs/architecture.md, roadmap, ADR-001 to ADR-054.

1. The whole system, step by step

Deployment view. Each step changes only what is highlighted. The step order is my suggestion; the roadmap doesn't order M4.

The diagrams keep their full size on narrow screens; scroll sideways inside each one.

Built

  • Pipeline: just data-real builds 727 signed files in about 8 minutes.
  • App: 9 commands; folder or HTTP source, verified and cached on disk.
  • Product site live; production key awaiting Riot.

Missing for players

  • No hosted data.
  • One patch (16.20), region all, elo master_plus.
  • No installer, updater or web viewer.

Changes

  • R2Publisher joins LocalPublisher behind the same Publisher port.
  • The app's data setting becomes the CDN URL; HttpSource already takes https://.

Why first

  • Smallest change (ADR-017: one adapter, one setting); steps 3 and 4 need a public URL.
  • Done when: the app runs on the CDN from an empty cache, then offline.

Changes

  • Same pipeline on a VPS timer, with the production key.
  • Signing key on the VPS only.
  • All champions, roles, elos, regions; paths already have {region}/{elo}.

Watch

  • A run below its floors should not publish.
  • Done when: a timer run publishes unattended.

Changes

  • Same UI with an HttpBackend reading the CDN (ADR-018), hosted with the site.
  • Read-only: no League client in a browser.

Blockers

  • Ranking runs in the Rust core (section 3).
  • Names and icons come from the client; the viewer needs Data Dragon.

Changes

  • CI builds signed installers and an update manifest for the Tauri updater.
  • Release public key in the app. App and data update independently.

Open

  • Updater key: a third secret.
  • Release host: GitHub Releases or R2.

3. Inside the desktop app

The UI only calls Backend.run(id, params); every core entry point dispatches through one registry. The web viewer is another backend; an MCP server would be another entry point.

Open question for the web viewer

The view renders build.plan, whose ranking lives in the Rust core (ADR-049). A browser has no core. Options:

  • Compile domain and the plan code to WebAssembly (recommended): one rule, and domain has no I/O.
  • publish writes ranked plans: simpler, but the rule is duplicated in Python.
  • Rewrite ranking in TypeScript: undoes ADR-049.

Same for names and icons, which come from the League client.

4. One champion select, end to end

The path under the 300 ms budget. The build is fetched and verified on hover, so lock-in is a cache hit plus the writes to the client.

5. How data is trusted

The app trusts the public key built into it, not the host. The CDN and serve-data go through HttpSource, shown here; a folder goes through DirectorySource, which runs the same two checks without the HTTP steps.
